## Context

類型設定頁面的「新增類型」表單目前只接受類型名稱；`bindSettingsActions` 建立的新類型固定以空的 `presetItems` 儲存。常用物品以 `{ id, name }` 存在 `state.commonItems`，類型預設物品則以 `{ id, name, qty }` 儲存；現有逐項加入流程會複製名稱並建立新的預設物品 ID，因此兩者沒有持續關聯。

這項變更服務旅行者快速建立可用的旅程類型：預設先把所有常用物品加入，再刪除不適用項目。PackCheck 必須維持原生 HTML/CSS/JavaScript、本機 `localStorage`、離線可用與手機優先的既有限制。

## Goals / Non-Goals

**Goals:**

- 在新增類型時，以預設勾選的單一選項控制是否批次套用目前全部常用物品。
- 以一次性快照產生合法的 `presetItems`，每項數量為 1 且有獨立 ID。
- 讓選項在手機、鍵盤與空常用物品狀態下都清楚且可預期。
- 保持既有類型、常用物品、匯入匯出與本機儲存資料格式相容。

**Non-Goals:**

- 不建立 `commonItemId` 關聯，也不讓後續常用物品變更同步到既有類型。
- 不提供部分勾選常用物品的多選器；使用者建立後沿用既有刪除功能調整清單。
- 不變更建立旅程時套用類型、合併多種類型或預設物品數量規則。
- 不重新設計類型設定頁面或引入新的色彩、字型、框架與相依套件。

## Decisions

### 在建立類型時採一次性快照複製

送出新增類型表單且選項為勾選時，依 `state.commonItems` 當下順序建立新的 `presetItems` 陣列。每個元素複製顯示名稱、將 `qty` 設為 1，並呼叫既有 ID 產生器取得獨立 ID。

這與目前由常用物品逐項建立預設物品的複製語意一致，也避免後續改名或刪除常用物品造成既有類型意外變動。替代方案是只儲存常用物品 ID 並動態解析名稱，但這會新增同步、缺失參照與資料遷移問題，且違反既有 copy-based 規格。

### 用原生核取方塊呈現預設啟用選項

在類型名稱輸入框與「新增類型」按鈕之間放置有明確 label 的原生 checkbox，文字為「將全部常用物品加入此類型」，初始為 checked。輔助文字顯示將加入的現有項目數量，整列 label 都可點擊，並沿用既有 CSS token、表單間距、焦點與海洋色系。

原生 checkbox 保留瀏覽器鍵盤、螢幕閱讀器與表單狀態語意。替代方案是切換按鈕，但會需要額外同步 `aria-pressed` 與視覺狀態，對單一布林選項沒有收益。

### 空常用物品時顯示停用狀態

當 `state.commonItems` 為空，checkbox 保持可見但為 disabled 且不勾選，輔助文字顯示「目前沒有常用物品可套用」。使用者仍能輸入名稱並建立空白類型。

保留控制項可讓使用者理解此功能存在及停用原因。完全隱藏選項雖較簡潔，但會讓空狀態與有資料狀態的表單結構不一致，也無法說明為何沒有批次套用。

### 保持現有資料結構與儲存流程

批次套用只改變建立新類型時傳入 `presetItems` 的內容，仍由現有 `state.tripTypes.push(...)` 與 `saveState()` 完成儲存。checkbox 是瞬時表單狀態，不寫入 `localStorage`；每次重新渲染新增類型表單時，依當下常用物品數量重設預設狀態。

這使現有匯入、匯出、驗證與遷移邏輯不需新增欄位或版本。替代方案是記住使用者上次選擇，但會改變「預設勾選」的明確需求並引入新的持久化設定。

## Implementation Contract

**Behavior**

- 常用物品至少一項時，新增類型表單顯示可操作且預設勾選的「將全部常用物品加入此類型」選項，並顯示目前項目數量。
- 保持勾選並成功建立類型時，新類型包含送出當下全部常用物品的快照，順序與常用物品清單一致，每項名稱不變、數量為 1、ID 各自唯一。
- 取消勾選並建立類型時，新類型的 `presetItems` 為空。
- 常用物品為空時，選項可見、disabled 且未勾選，使用者仍可建立空白類型。
- 類型建立後，常用物品的新增、改名或刪除不修改該類型的預設物品。

**Interface and data shape**

- 不新增持久化欄位。`commonItems` 維持 `{ id, name }[]`，`tripTypes[].presetItems` 維持 `{ id, name, qty }[]`。
- 新控制項必須具有可由 label 存取的 checkbox 語意、清楚的停用狀態與輔助文字；鍵盤焦點必須可見。
- 送出時只讀取表單當下的 checkbox 狀態與 `state.commonItems` 快照。

**Failure modes**

- 類型名稱空白時沿用既有錯誤，不建立類型，也不消耗批次複製結果。
- `state.commonItems` 缺少或不是陣列時，視為空清單並建立空白類型，不拋出未處理例外。
- 儲存失敗處理維持現有行為；本變更不新增獨立錯誤訊息或遠端重試。

**Acceptance criteria**

- 自動化測試涵蓋預設勾選批次套用、取消勾選、空常用物品、數量固定為 1、獨立 ID，以及後續常用物品變更不回寫既有類型。
- 在 320 px 與 390 px 寬度手動確認選項與主要按鈕無水平溢位、整列可點擊、checkbox 可由鍵盤切換且焦點可見。
- 現有資料匯入匯出與相關測試持續通過。

**Scope boundaries**

- 範圍內：新增類型表單、建立類型事件處理、批次快照轉換、相關樣式與驗證。
- 範圍外：常用物品管理頁重設計、持續同步、部分選取、旅程建立流程、資料格式版本與雲端功能。

## Risks / Trade-offs

- [大量常用物品會一次產生較長的預設清單] → 顯示即將加入的數量，並保留取消勾選與建立後逐項刪除。
- [重新渲染表單會恢復預設勾選] → 將 checkbox 明定為每次建立操作的預設值，不保存未送出的 UI 選擇。
- [常用物品在送出前被其他程式路徑更新] → 以送出當下的 `state.commonItems` 建立單一快照，避免讀取不同時間點的資料。
- [新增選項壓縮手機版表單] → 使用單欄全寬選項列並在 320 px、390 px 驗證無水平溢位。

## Migration Plan

不需要資料遷移。部署後既有類型與常用物品保持不變，只有新建立的類型會採用新預設。若需回滾，可移除 checkbox 與批次建構邏輯；已建立類型中的預設物品仍是合法既有資料，不需清理。

## Open Questions

無；預設狀態、空清單行為、複製語意、數量與同步邊界均已在討論中確定。
